# Unified Coding Guidelines

Combined principles from **Karpathy**, **Vibe**, and **Superpowers** for reliable, methodical task execution.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

---

## Foundation: Karpathy Behavioral Guidelines

### 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If 200 lines could be 50, rewrite it.

Ask: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it — don't delete it.

When your changes create orphans: Remove only what YOUR changes made unused.

**Test:** Every changed line should trace directly to the user's request.

### 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

## Workflow: Vibe Governed Process

### Task Complexity Grades

| Grade | Scope | Characteristics |
|-------|-------|------------------|
| **M** | Narrow, focused | Single step, clear boundaries — simplify workflow |
| **L** | Medium complexity | Multi-step, needs planning |
| **XL** | Large, parallelizable | Split into bounded units |

### Phase 1: Clarify

**Clarify before coding.**

- State the problem clearly
- Identify what success looks like
- Confirm scope and boundaries
- **Frozen Requirement**: Once confirmed, won't silently change

### Phase 2: Plan

**Plan before executing.**

- Break down into concrete steps
- Define verification for each step
- Keep the plan minimal

### Phase 3: Execute

**Execute the plan. Stay disciplined.**

- Follow the plan unless there's clear reason to deviate
- If deviation needed, return to Clarify phase
- Keep changes surgical

### Phase 4: Verify

**Verify before delivery.**

- Test against original requirement
- Check all checkpoints pass
- Confirm no unintended side effects

### Safety Rules

- **No blind execution**: Always clarify before coding
- **No silent scope creep**: Frozen requirements stay frozen
- **No bulk deletion**: Dangerous ops require explicit confirmation
- **No silent fallbacks**: If something fails, say it explicitly

## Methodology: Superpowers Development Process

### Phase 1: Brainstorming (Spec Before Code)

**"Tease out a spec before writing code."**

- Use Socratic questioning to refine ideas
- Explore alternatives and tradeoffs
- Present design in chunks for validation
- Save approved design to document

### Phase 2: Writing Plans (Bite-sized Tasks)

**"Plan clear enough for a junior engineer to follow."**

Every task includes:
- Exact file paths to modify
- Complete code or change description
- Verification steps

```
## Task N: [Brief Description]
### Files: [exact paths]
### Change: [what to do]
### Verify: [how to confirm it works]
```

### Phase 3: Test-Driven Development

**RED-GREEN-REFACTOR cycle:**

1. **RED**: Write failing test first
2. **GREEN**: Write minimal code to pass
3. **REFACTOR**: Clean up while keeping tests green

**Rule:** Delete any code written before tests.

### Phase 4: Code Review

**Review against plan, report by severity:**

| Level | Action |
|-------|--------|
| Critical | Block progress |
| Major | Fix before moving on |
| Minor | Note and continue |

Two-stage review:
1. **Spec compliance**: Does it match the task?
2. **Code quality**: Is it simple? Any smells?

### Phase 5: Systematic Debugging (When Broken)

4-phase process:
1. **Reproduce**: Make failure consistent
2. **Isolate**: Narrow down to exact cause
3. **Fix**: Apply minimal fix
4. **Verify**: Confirm fix works, no regressions

## Summary: How These Work Together

| Framework | Focus | When |
|-----------|-------|------|
| **Karpathy** | Code behavior | Every code change |
| **Vibe** | Task workflow | Every task |
| **Superpowers** | Development method | Building features |

**Universal rule:** Clarify → Plan → Execute (with TDD) → Verify → Review

---

**These guidelines are working if:** fewer unnecessary changes, fewer rewrites, clarifying questions come before implementation, every task follows the governed workflow, and tests are written before code.
