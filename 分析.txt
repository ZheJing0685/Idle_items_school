Idle Items School 项目审视报告
一、架构概览
前端: Vue 3.5 + Vite 8 + Element Plus + Pinia + Vue Router 4 + ECharts
后端: Spring Boot 3.2.4 + Spring Security + JPA/Hibernate + MySQL 8 + Redis + Flyway + WebSocket
部署: Docker Compose (Nginx + Spring Boot + MySQL)
复制
分层结构总体合理，前后端通过 /api 前缀解耦，Vite dev proxy 和 Nginx 生产代理各司其职。

二、做得好的地方
1. API 路径统一管理
后端 ApiPaths.java 和前端 paths.js 分别维护路径常量，改接口只需改一处。这个习惯值得保留。

2. 请求合并与缓存（前端）
RequestManager 实现了请求去重（useMerge）和客户端缓存（useCache），避免了短时间内重复请求。对商品列表、热门商品这类读多写少的场景很实用。

3. Flyway 数据库版本管理
16 个 migration 脚本，从初始 schema 到索引优化到数据初始化，版本演进有迹可循。比手动执行 SQL 靠谱得多。

4. 数据库索引设计
Item 和 Order 实体上定义了复合索引（如 user_id + status、category_id + status），说明对查询模式做过思考。

5. 全局异常处理
GlobalExceptionHandler 覆盖了从参数校验到运行时异常的完整链路，前端也有对应的 ErrorHandler 做分类展示。前后端的错误处理形成了闭环。

6. XSS 过滤 + 限流
XssFilter 和 RateLimitFilter 作为 Servlet Filter 注册，在请求进入 Controller 之前就拦截。限流用 Redis Lua 脚本实现，原子性有保障。

三、关键问题
P0：必须立即修复
1. JWT Secret 硬编码默认值

# application-dev.yml
jwt:
  secret: ${JWT_SECRET:idle-items-school-dev-secret-key-2024-for-jwt-token}
复制
这个默认值在代码仓库里明文可见。如果有人忘记设环境变量就部署，任何人都能伪造 token。即使只在 dev profile 里，也应该在启动时检查 secret 是否为默认值并拒绝启动，或者直接不设默认值让启动失败。

2. 敏感凭据明文存储

jian.md 里写着数据库 root 密码和管理员账号密码。docker-compose.yml 里 MYSQL_ROOT_PASSWORD: root。这些文件会被 git 追踪。需要：

将 jian.md 加入 .gitignore 并从 git 历史中清除
docker-compose 改用 .env 文件注入密码
数据库密码和 JWT secret 通过环境变量注入，不设默认值
3. SecurityConfig 和 WebSecurityConfig 重复

两个安全配置类同时存在。SecurityConfig 负责认证链和 JWT Filter，WebSecurityConfig 负责 XSS、限流和 CORS。问题在于两者职责界限模糊，新人维护时容易在错误的地方改配置。应该合并为一个 SecurityConfig，内部用 @Order 区分 Filter 优先级。

4. CORS 配置过于宽松

config.addAllowedOriginPattern("*");
config.addAllowedHeader("*");
config.addAllowedMethod("*");
复制
在开发阶段可以接受，但生产环境必须限制为实际的前端域名。addAllowedOriginPattern("*") 配合 setAllowCredentials(true) 在某些浏览器版本中会被拒绝。

P1：影响可维护性和正确性
5. Service 层职责越界

ItemService 直接操作 UserRepository 填充卖家信息，ItemController 也调用 UserInfoService 填充同样的信息。同一个"填充卖家信息"的逻辑分散在两个地方。应该由一个专门的 DTO 转换层或 @EntityGraph 统一处理。

6. 缓存层有两个类职责重叠

CacheService（在 cache 包下）和 CacheManager（在 util 包下）都封装了 Redis 操作。CacheManager 的 deletePattern 用 SCAN，CacheService 的 deletePattern 用 KEYS。两者混用会导致缓存清除不一致。应该只保留一个。

7. 缓存的 Page 对象序列化风险

// ItemService.java
cacheManager.set(cacheKey, dtoPage, 300); // 缓存 Page<ItemSummaryDTO>
复制
Spring Data 的 PageImpl 包含 Pageable 等复杂对象，Redis 序列化/反序列化容易出问题（特别是换了序列化策略后）。应该缓存查询结果的 List + totalElements，反序列化时手动重建 Page。

8. 前端 Token 管理混乱

axios.js 里用 cookie 存 token（setCookie('user:token', ...)），但 user.js store 里用 storage.getStorage('persistent') 也存 token。errorHandler.js 清理时只清 localStorage。如果 cookie 里有旧 token 但 localStorage 被清了，会出现状态不一致。

建议统一为一种存储方式。如果用 cookie 就全部用 cookie，store 里不再额外存一份。

9. createItem/updateItem 用 Map 接收参数

public Item createItem(Long userId, Map<String, Object> request) throws Exception {
    item.setTitle((String) request.get("title"));
    item.setPrice(request.get("price") != null ? new BigDecimal(request.get("price").toString()) : null);
    // ... 30 行手动取值
复制
没有类型安全，没有参数校验（@Valid 不生效），字段名拼错也不会报编译错误。应该定义 CreateItemRequest DTO，加上 @NotBlank、@NotNull 等校验注解。

10. Nginx 配置端口不一致

docker-compose.yml 里 backend 映射 8080:8080，但 nginx.conf 里 proxy_pass 写的是  Spring Boot 实际监听 7000 端口（server.port: 7000）。Docker 部署时请求会打到错误端口。

P2：提升代码质量
11. Entity 上的 @Transient 卖家信息

@Transient
private String sellerNickname;
@Transient
private boolean sellerVerified;
@Transient
private Double sellerRating;
@Transient
private Integer sellerItemsCount;
复制
Entity 承载了展示层的数据，违反单一职责。应该用 DTO 返回这些字段，Entity 保持纯数据库映射。

12. 前端 Dockerfile 用 Node 14

FROM node:14-alpine as build
复制
package.json 里依赖的是 Vue 3.5、Vite 8，这些要求 Node 18+。Node 14 已经 EOL。应该改为 node:20-alpine 或 node:22-alpine。

13. 缺少 i18n 实际使用

package.json 里有 vue-i18n 依赖，但 main.js 里没有初始化 i18n，代码里也没有语言文件。要么用起来，要么移除减少包体积。

14. 后端缺少输入校验注解

AuthController 的 LoginRequest 和 RegisterRequest 用了 @Valid，但 ItemController 的 createItem 接收 Map<String, Object> 绕过了校验。校验体系形同虚设。

15. 刷新 Token 机制不完善

refreshToken 的生成没有用独立的 secret 或更长的过期时间区分于 access token。当前实现中 refresh token 和 access token 的唯一区别是 claims 里少了 username 和 role，但验证逻辑完全一样。如果 access token 泄露，refresh token 也无法提供额外保护。

四、总结
项目骨架搭得不错，分层、配置管理、数据库版本控制都有模有样。主要风险集中在安全凭据管理和前后端状态一致性上。代码质量方面，最大的技术债是 Map<String, Object> 接收参数和两个缓存类并存。
