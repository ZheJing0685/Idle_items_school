# 数据库迁移方案

## 一、迁移工具选择

选择 **Flyway** 作为数据库版本管理和迁移工具，原因如下：

- **简单易用**：基于文件系统的版本控制，配置简单
- **可靠性高**：支持事务和回滚，确保迁移的原子性
- **与Spring Boot集成良好**：项目使用Spring Boot，集成方便
- **版本控制**：自动管理迁移脚本的执行状态

## 二、迁移策略

采用 **增量迁移** 策略，具体步骤如下：

1. **备份现有数据库**：在迁移前执行完整备份
2. **创建基础迁移脚本**：针对现有表结构的初始版本
3. **编写增量迁移脚本**：按优先级分阶段执行
4. **数据验证**：迁移后验证数据一致性
5. **回滚机制**：准备回滚脚本，应对异常情况

## 三、迁移脚本结构

```
src/main/resources/db/migration/
├── V1__initial_schema.sql       # 初始表结构
├── V2__add_core_fields.sql       # 添加核心字段（高优先级）
├── V3__add_optional_fields.sql   # 添加可选字段（中低优先级）
├── V4__add_new_tables.sql        # 添加新表
└── V5__data_initialization.sql   # 数据初始化
```

## 四、详细迁移步骤

### 1. 准备阶段

- **环境准备**：
  - 安装并配置Flyway
  - 配置数据库连接信息
  - 创建测试环境用于验证

- **数据备份**：
  - 执行完整数据库备份
  - 验证备份文件完整性

### 2. 执行阶段

**步骤1：执行初始迁移（V1）**
- 创建现有表结构
- 确保基础数据完整性

**步骤2：添加核心字段（V2）**
- 所有表的逻辑删除字段(is_deleted)
- 所有表的审计字段(create_by/update_by)
- users表的信用相关字段
- orders表的金额和物流相关字段

**步骤3：添加可选字段（V3）**
- users表的登录相关字段
- items表的议价和推荐相关字段
- chats表的消息统计字段
- verification_records表的扩展字段

**步骤4：添加新表（V4）**
- user_addresses表
- user_follows表
- notifications表
- system_configs表
- operation_logs表

**步骤5：数据初始化（V5）**
- 为新增字段设置默认值
- 初始化系统配置数据
- 填充必要的基础数据

### 3. 验证阶段

- **数据一致性检查**：
  - 比对迁移前后的记录数
  - 验证关键业务数据的完整性
  - 检查外键关系的正确性

- **功能验证**：
  - 执行核心业务流程测试
  - 验证新字段的功能
  - 测试新增表的使用

## 五、数据备份方案

### 1. 备份策略

- **全量备份**：迁移前执行完整数据库备份
- **增量备份**：迁移过程中定期执行增量备份
- **差异备份**：记录迁移前后的数据差异

### 2. 备份方法

- **MySQL命令行**：使用`mysqldump`工具
  ```bash
  mysqldump -u root -p idle_items_school > backup_$(date +%Y%m%d_%H%M%S).sql
  ```

- **Flyway备份**：利用Flyway的版本控制功能

- **物理备份**：直接复制数据文件（适合停机迁移）

## 六、回滚方案

### 1. 回滚策略

- **逐版本回滚**：按迁移版本的相反顺序执行回滚
- **完整回滚**：使用备份文件恢复到迁移前状态

### 2. 回滚脚本

为每个迁移版本准备对应的回滚脚本：

```
src/main/resources/db/migration/
├── U1__initial_schema.sql       # 初始表结构回滚
├── U2__add_core_fields.sql       # 核心字段回滚
├── U3__add_optional_fields.sql   # 可选字段回滚
├── U4__add_new_tables.sql        # 新表回滚
└── U5__data_initialization.sql   # 数据初始化回滚
```

## 七、迁移风险评估

### 1. 潜在风险

- **数据丢失**：迁移过程中数据损坏或丢失
- **性能影响**：迁移过程中系统响应缓慢
- **业务中断**：迁移期间系统不可用
- **兼容性问题**：新字段与现有代码不兼容

### 2. 风险缓解措施

- **充分测试**：在测试环境验证迁移脚本
- **分批执行**：按优先级分批次执行迁移
- **监控机制**：迁移过程中实时监控
- **回滚准备**：准备详细的回滚方案
- **业务协调**：选择业务低峰期执行迁移

## 八、迁移时间计划

| 阶段 | 时间估计 | 主要任务 |
|------|----------|----------|
| 准备阶段 | 1天 | 环境准备、数据备份 |
| 执行阶段 | 2天 | 执行迁移脚本 |
| 验证阶段 | 1天 | 数据验证、功能测试 |
| 上线阶段 | 0.5天 | 生产环境部署 |

## 九、迁移后维护

- **监控**：监控数据库性能和数据完整性
- **优化**：根据实际使用情况优化索引和查询
- **文档**：更新数据库文档，记录迁移过程
- **培训**：对开发人员和运维人员进行培训

## 十、总结

本迁移方案采用增量迁移策略，使用Flyway作为迁移工具，确保数据的完整性和系统的稳定性。通过分阶段执行迁移，降低了风险，提高了成功率。同时，完善的备份和回滚机制确保了在出现异常情况时能够快速恢复系统。

迁移完成后，数据库将具备更完整的功能支持、更好的可维护性和可扩展性，为平台的持续发展奠定基础。
