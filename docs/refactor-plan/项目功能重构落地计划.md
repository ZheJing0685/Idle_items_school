## 一、重构目标与愿景

### 1.1 愿景

将闲置物品校园交易平台从"基础框架可用"提升至"生产级可部署"状态，建立安全、高效、可维护的技术基座，支撑校园闲置物品交易的完整业务闭环。

### 1.2 量化目标

| 维度 | 指标 | 当前状态 | 目标值 | 验收方法 |
|------|------|----------|--------|----------|
| **功能完整性** | 核心交易流程覆盖率 | ~60%（订单/评价/聊天已有实体但流程不完整） | 100%（发布→浏览→下单→支付→收货→评价闭环） | E2E 测试通过 |
| **安全性** | 高危漏洞数 | ≥3（JWT 硬编码、CORS 全开、敏感信息明文） | 0 | OWASP ZAP 扫描 |
| **性能** | API P95 响应时间 | 未测量 | ≤500ms | JMeter 压测 |
| **性能** | 首页加载时间 | 未优化 | ≤2s | Lighthouse ≥85 |
| **代码质量** | 后端单元测试覆盖率 | 极低 | ≥70% | JaCoCo 报告 |
| **代码质量** | 前端单元测试覆盖率 | ~8% | ≥60% | Vitest 覆盖率 |
| **部署** | Docker 一键部署成功率 | 0%（多处配置错误） | 100% | `docker-compose up` 验证 |
| **用户体验** | 移动端适配 | 基础响应式 | 完美适配主流设备 | 多设备测试 |

### 1.3 核心原则

1. **渐进式重构** — 不做大规模重写，每次变更保持系统可运行
2. **测试先行** — 重构前补充关键路径测试，确保变更不引入回归
3. **安全优先** — P0 安全问题必须在功能开发前修复
4. **文档同步** — 每次重构变更同步更新 Code Wiki 文档

## 四、模块重构方案

### 4.1 后端模块重构方案

#### 4.1.1 Security 配置合并

**现状**：`SecurityConfig` 和 `WebSecurityConfig` 两个配置类职责交叉。

**方案**：合并为单一 `SecurityConfig`，职责划分：
- CORS 配置
- 密码编码器
- 认证管理器
- CSRF 策略
- 会话管理（STATELESS）
- 白名单路径
- JWT 过滤器注册

**涉及文件**：
- `backend/src/main/java/.../config/SecurityConfig.java` — 保留并扩展
- `backend/src/main/java/.../config/WebSecurityConfig.java` — 合并后删除

**验证方法**：所有现有 API 端点权限行为不变，单元测试通过。

#### 4.1.2 JWT 安全加固

**现状**：密钥硬编码，无 Refresh Token，Token 黑名单依赖 Redis 但 Redis 未部署。

**方案**：
1. `JwtUtil` 改造：密钥从 `@Value("${jwt.secret}")` 读取
2. 新增 `generateRefreshToken()` / `validateRefreshToken()` 方法
3. `AuthServiceImpl` 改造：登录时同时返回 accessToken 和 refreshToken
4. `/auth/refresh` 端点实现：验证 refreshToken → 生成新 accessToken
5. Token 黑名单使用 Redis SET，key 为 `token:blacklist:{tokenHash}`，TTL 与 Token 一致

**涉及文件**：
- `backend/src/main/java/.../security/JwtUtil.java`
- `backend/src/main/java/.../service/impl/AuthServiceImpl.java`
- `backend/src/main/java/.../controller/AuthController.java`
- `backend/src/main/resources/application-dev.yml`
- `backend/src/main/resources/application-prod.yml`

**验证方法**：
- 登录返回双 Token
- refreshToken 可刷新 accessToken
- 登出后 Token 加入黑名单，请求返回 401

#### 4.1.3 Service 层整理

**现状**：
- `UserService` + `UserInfoService` 职责重叠
- `ImageUtil` + `FileServiceImpl` + `ImageProcessingService` 图片处理分散

**方案**：
1. 将 `UserInfoService` 的查询方法合并到 `UserService`，删除 `UserInfoService`
2. 将 `ImageUtil` 的工具方法合并到 `FileServiceImpl`，`ImageProcessingService` 作为内部处理器保留，删除 `ImageUtil`

**涉及文件**：
- `backend/src/main/java/.../service/UserService.java`
- `backend/src/main/java/.../service/UserInfoService.java` — 删除
- `backend/src/main/java/.../service/impl/FileServiceImpl.java`
- `backend/src/main/java/.../util/ImageUtil.java` — 删除
- 所有引用上述类的 Controller 和 Service

**验证方法**：编译通过，现有功能测试通过。

#### 4.1.4 缓存策略统一

**现状**：`CacheManager`（自定义）和 `CacheService`（Redis 通用操作）并存，部分 Service 直接操作 Redis，部分使用 `CacheManager`。

**方案**：
1. `CacheManager` 作为业务缓存策略层，定义缓存键和过期时间
2. `CacheService` 作为 Redis 操作层，提供底层 CRUD
3. Service 层统一通过 `CacheManager` 操作缓存，不再直接调用 `CacheService`

**涉及文件**：
- `backend/src/main/java/.../util/CacheManager.java`
- `backend/src/main/java/.../cache/CacheService.java`
- 各 Service 实现类

## 七、兼容过渡方案

### 7.1 总体策略

采用**渐进式重构**策略，每个模块独立交付，确保系统在重构过程中始终可运行。

```
旧代码 ──→ [并行运行] ──→ 新代码 ──→ [验证通过] ──→ 移除旧代码
```

### 7.2 API 兼容性

| 场景 | 过渡策略 |
|------|----------|
| JWT 双 Token 改造 | 旧 Token 格式继续支持，新格式渐进启用。前端先适配 refreshToken，后端同时接受新旧格式 |
| SecurityConfig 合并 | 合并前后 API 权限行为保持一致，通过测试用例验证 |
| Service 层合并 | 保留旧类作为 `@Deprecated` 代理，内部委托到新实现，验证通过后删除 |

### 7.3 数据库兼容性

| 场景 | 过渡策略 |
|------|----------|
| 新增 Entity 映射已有表 | 仅新增 Entity 类，不修改已有表结构，JPA `validate` 模式验证 |
| 清理冗余字段 | 先确认数据迁移完成，再通过新 Flyway 脚本（V17+）移除字段 |
| 新增索引 | 通过 Flyway 脚本添加，`CREATE INDEX IF NOT EXISTS` 避免重复 |

### 7.4 部署兼容性

| 场景 | 过渡策略 |
|------|----------|
| Docker 配置修复 | 一次性修复所有已知问题，修复前后通过 `docker-compose config` 验证 |
| Redis 集成 | 后端已有 Redis 配置，仅需在 docker-compose 中添加服务。后端启动时检测 Redis 不可用则降级为内存缓存 |
| 端口映射修复 | 统一为 7000 端口，Nginx 代理目标同步更新 |

### 7.5 回滚方案

| 模块 | 回滚方式 |
|------|----------|
| Docker 修复 | `git revert` 回退 Docker 相关文件 |
| 安全加固 | JWT 密钥回退到配置文件（仅开发环境），CORS 回退到允许所有 |
| 后端架构整理 | 保留旧类的 `@Deprecated` 代理，回滚时恢复旧类 |
| 前端架构整理 | Git 分支管理，回滚到整理前的分支 |
| 数据库优化 | Flyway 不支持回滚，新增脚本使用 `IF EXISTS` / `IF NOT EXISTS` 保证幂等 |

### 7.6 灰度发布策略

1. **开发环境**：所有重构变更首先在本地开发环境验证
2. **Docker 环境**：通过 `docker-compose` 在本地模拟生产环境验证
3. **CI/CD 验证**：PR 合并前自动运行测试套件
4. **生产部署**：main 分支合并后自动部署（CI/CD 完善后）
