## 1. 项目概述与改进目标

### 1.1 项目现状

校园闲置物品交易系统是一个基于前后端分离架构的校园C2C电商平台，目前已完成基础框架搭建，但存在以下关键问题：

- **实体层严重缺失**：数据库15张表仅有3个Java实体，导致订单、评价、收藏等核心功能无法运行
- **安全配置不合规**：JWT密钥硬编码、无刷新机制、CORS全开放等安全隐患
- **测试覆盖率极低**：前端测试覆盖率仅8%，E2E测试存在失败用例
- **开发体验不佳**：Vite无代理配置、环境配置硬编码
- **功能不完整**：缺少聊天、纠纷处理等关键业务模块

### 1.2 总体改进目标

通过本次全面改进，达到以下目标：

1. **功能完整性**：实现完整的校园闲置物品交易全流程
2. **系统稳定性**：关键功能可用性达到99.9%，核心流程端到端测试通过率100%
3. **性能表现**：页面加载时间≤2秒，API响应时间≤500ms（P95）
4. **安全性**：通过基础安全审计，无高危安全漏洞
5. **代码质量**：测试覆盖率≥70%，代码规范检查通过率100%
6. **用户体验**：用户满意度评分≥4.5/5.0

### 1.3 核心价值主张

1. **为学生提供安全便捷的交易平台**：完善的身份验证、交易保障和纠纷处理机制
2. **提升校园资源利用率**：促进闲置物品流通，减少资源浪费
3. **构建校园数字社区**：通过聊天互动、评价系统增强用户粘性
4. **建立可维护的技术基座**：为后续功能扩展和性能优化奠定基础

## 3. 详细改进方案

### 3.1 基础架构修复（P0）

#### 3.1.1 实体层补充与重构

**问题**：数据库15张表仅有3个Java实体（User、Item、ImageAnalysis），导致订单、评价、收藏等功能无法运行。

**目标**：补充所有缺失的实体类，建立完整的实体-数据库映射关系。

**实施步骤**：

1. **实体类创建**（按依赖顺序）：
   ```
   Step 1: Category.java → 物品分类（Item.categoryId外键依赖）
   Step 2: Order.java → 订单（关联User和Item）
   Step 3: Review.java → 评价（关联User、Item、Order）
   Step 4: Favorite.java → 收藏（关联User和Item）
   Step 5: ItemImage.java → 物品图片（关联Item）
   Step 6: ItemTag.java → 物品标签（关联Item）
   Step 7: Chat.java → 聊天会话（关联User）
   Step 8: ChatMessage.java → 聊天消息（关联Chat和User）
   Step 9: Dispute.java → 纠纷（关联Order和User）
   Step 10: VerificationRecord.java → 认证记录（关联User）
   ```
2. **Repository层适配**：
   - 为每个新实体创建对应的JPA Repository接口
   - 补充必要的自定义查询方法
3. **Service层验证**：
   - 验证已有Service层方法与新实体的兼容性
   - 补充必要的业务逻辑方法
4. **数据库映射验证**：
   - 配置`spring.jpa.hibernate.ddl-auto: validate`
   - 运行应用验证实体-表映射关系
   - 修复映射错误和不一致

**技术选型**：

- 继续使用Spring Data JPA作为ORM框架
- 使用Lombok简化实体类代码
- 使用Jakarta Persistence 3.1注解

**预期效果**：

- 所有数据库表都有对应的Java实体
- JPA能够正常执行CRUD操作
- 现有Controller和Service层代码可正常运行

**验证方法**：

1. 单元测试：为每个实体类创建基本的CRUD测试
2. 集成测试：验证实体关联关系和级联操作
3. 端到端测试：运行完整的交易流程测试

#### 3.1.2 JWT安全加固

**问题**：JWT密钥硬编码、无Refresh Token机制、无Token黑名单、CORS全开放。

**目标**：建立符合安全标准的JWT认证体系。

**实施步骤**：

1. **密钥管理改造**：
   ```yaml
   # application.yml 改造
   jwt:
     secret: ${JWT_SECRET:default-fallback-secret}  # 环境变量优先
     access-expiration: 3600000      # Access Token 1小时
     refresh-expiration: 604800000   # Refresh Token 7天
   ```
2. **双Token机制实现**：
   ```java
   // JwtUtil.java 改造
   public String generateAccessToken(Long userId, String username, String role) {
       // 短期Token，仅包含必要信息
   }

   public String generateRefreshToken(Long userId) {
       // 长期Token，存储到Redis或数据库
   }

   public boolean validateRefreshToken(String token) {
       // 验证Refresh Token有效性
   }
   ```
3. **Token黑名单机制**：
   - 用户登出时将Token加入黑名单（Redis存储，TTL与Token过期时间一致）
   - JWT Filter验证Token时检查黑名单
4. **CORS安全配置**：
   ```java
   // SecurityConfig.java 改造
   @Bean
   public CorsConfigurationSource corsConfigurationSource() {
       CorsConfiguration config = new CorsConfiguration();
       config.setAllowedOrigins(Arrays.asList(
           "http://localhost:5173",      // 开发环境
           "https://idleitems.school",   // 生产环境
           "https://admin.idleitems.school"
       ));
       config.setAllowedMethods(Arrays.asList("GET", "POST", "PUT", "DELETE", "OPTIONS"));
       config.setAllowedHeaders(Arrays.asList("*"));
       config.setAllowCredentials(true);
       config.setMaxAge(3600L);
       
       UrlBasedCorsConfigurationSource source = new UrlBasedCorsConfigurationSource();
       source.registerCorsConfiguration("/api/**", config);
       return source;
   }
   ```
5. **API刷新端点完善**：
   ```java
   @PostMapping("/refresh")
   public Result<Map<String, Object>> refreshToken(
           @RequestHeader("Authorization") String authHeader) {
       // 1. 验证Refresh Token
       // 2. 生成新的Access Token
       // 3. 可选：生成新的Refresh Token（滚动刷新）
   }
   ```

**技术选型**：

- 继续使用jjwt 0.12.3（已修复历史安全漏洞）
- Redis用于Token黑名单存储（使用Spring Data Redis）
- 环境变量管理：Spring Boot Environment Abstraction

**预期效果**：

- JWT密钥通过环境变量管理，无硬编码风险
- 支持Token刷新，用户无需频繁重新登录
- 登出后Token立即失效，增强安全性
- CORS限制到可信域名，减少CSRF风险

**验证方法**：

1. 安全扫描：使用OWASP ZAP进行API安全测试
2. Token测试：验证Access/Refresh Token流程
3. 黑名单测试：验证登出后Token失效

#### 3.1.3 API层与Store存储统一

**问题**：`api/index.js`硬编码`localStorage.getItem('token')`，而UserStore使用抽象存储层，导致存储策略不一致。

**目标**：统一Token存储访问，确保前后端存储策略一致。

**实施步骤**：

1. **前端API层改造**：
   ```javascript
   // api/index.js 改造
   import { userStore } from '../store'

   instance.interceptors.request.use((config) => {
     const store = userStore()
     if (store.token) {
       config.headers.Authorization = `Bearer ${store.token}`
     }
     return config
   })
   ```
2. **存储抽象层优化**：
   - 确保Storage.js的`getStorage()`方法支持所有存储类型
   - 添加类型检查和错误处理
3. **配置同步机制**：
   - 在应用初始化时统一设置存储类型
   - 确保Store和API层使用相同的存储实例

**技术选型**：

- 保持现有Pinia + Storage.js架构
- 增加TypeScript类型定义（如迁移到TypeScript）

**预期效果**：

- Token存储策略完全一致，避免潜在Bug
- 支持灵活的存储策略切换（localStorage/sessionStorage/cookie）
- 为未来SSR架构预留支持

**验证方法**：

1. 功能测试：使用不同存储策略测试登录流程
2. 兼容性测试：验证各浏览器下的存储行为

   - **应对**：建立质量门禁，关键功能必须有测试
3. **人员风险**：关键人员离职影响进度
   - **应对**：知识共享，文档化，交叉培训
